Critique C-01 · confirmé en production

Le secret JWT de production est publié sur GitHub

Le dépôt AJC-PoleSI/RH-Manager est public, et deux fichiers suivis par git contenaient la clé JWT_SECRET de production en clair. Cette clé est celle qui signe les jetons de session : n'importe qui, sur Internet, pouvait forger un jeton administrateur valide et obtenir un accès total à la plateforme — lire les coordonnées de tous les candidats, modifier des notes, changer des décisions de délibération.

$ grep -rl "<secret>" --include="*.ts" . run-simulation.ts simulate-load-real.ts $ gh repo view --json visibility {"nameWithOwner":"AJC-PoleSI/RH-Manager","visibility":"PUBLIC"} # la clé trouvée dans ces fichiers est identique à JWT_SECRET de frontend/.env.local

J'ai retiré la clé des deux fichiers (ils lisent désormais process.env.JWT_SECRET), mais elle reste dans 3 commits de l'historique public : la retirer du code ne la révoque pas.

À faire par toi Régénérer JWT_SECRET dans les variables d'environnement Vercel, puis redéployer. Toutes les sessions en cours seront déconnectées — à faire hors créneau d'épreuve. Passer le dépôt en privé serait une seconde ceinture, mais la rotation reste indispensable : la clé a été publique.
Critique C-02 · reproduit

Un candidat peut lister tous les autres candidats et leur jury

La route GET /api/slots/all ne vérifie qu'une chose : que l'appelant soit authentifié. Elle renvoie donc à un candidat exactement la même charge utile qu'à l'admin — le planning complet avec, pour chaque créneau, l'identité des examinateurs affectés et celle des candidats inscrits.

GET /api/slots/all (jeton candidat « Alice Martin ») → 200 exposé : bilal.nguyen@… · Nguyen · chloe.dupont@… · Dupont david.rossi@… · Rossi examinateur01@ajc-mail.com · examinateur02@… · examinateur03@… # source : le seul contrôle est `if (!payload) return unauthorized()`

Deux conséquences : une fuite de données personnelles (nom, prénom, adresse mail de chaque candidat, accessible à tous les autres), et une rupture d'équité — un candidat peut connaître à l'avance la composition de son jury et se renseigner sur les examinateurs.

Correctif Refuser le rôle candidate sur cette route, comme le font déjà /api/candidates et /api/deliberations. Les candidats ont déjà /api/slots/available et /api/slots/my-enrollments, qui sont correctement filtrés.
Élevé H-01 · confirmé en production

La page KPI par pôle renvoie une erreur 500

GET /api/kpis/poles lit une colonne deliberations.assigned_pole qui n'existe dans aucune migration du dépôt — et que j'ai vérifiée absente de la base de production. La route échoue donc systématiquement, pour l'admin comme pour les examinateurs.

GET /api/kpis/poles (admin) → 500 {"error":"Failed to fetch pole KPIs"} serveur : column deliberations.assigned_pole does not exist (code 42703) # vérification schéma production (lecture seule) : ABSENTE deliberations.assigned_pole PRÉSENTE epreuves.color · epreuves.description PRÉSENTE candidate_wishes.tour · candidates.wishes_locked_at

Au passage : assigned_pole n'est écrit par aucune route de l'application. Même une fois la colonne créée, le compteur « places acceptées » de cet écran restera à zéro tant que l'affectation de pôle en délibération n'est pas implémentée.

Correctif Ajouter ALTER TABLE deliberations ADD COLUMN IF NOT EXISTS assigned_pole TEXT; à MIGRATIONS_A_APPLIQUER.sql — ou, si l'affectation de pôle n'est plus au programme, retirer la colonne des deux requêtes qui la lisent.
Élevé H-02 · reproduit

Les mails de résultats sont comptés comme envoyés même quand aucun ne part

Toutes les fonctions de lib/resend.ts font return resend.emails.send(…) sans jamais examiner ce que le SDK renvoie. Or le SDK Resend ne rejette pas en cas d'échec : il résout avec { data: null, error: {…} }. Comme deliberations/validate compte les succès avec Promise.allSettled, un échec total remonte comme un succès total.

await resend.emails.send({…}) // clé invalide → la promesse RÉSOUT data : null error : {"statusCode":401,"name":"validation_error","message":"API key is invalid"} POST /api/deliberations/validate → 200 {"ok":true,"tour":3,"sent":1,"failed":0} ▲ aucun mail n'est parti

Concrètement : tu valides la soirée de délibération, l'interface affiche « N mails envoyés », et les candidats n'apprennent jamais leur résultat. Le même défaut touche les mails de vérification d'adresse, de réinitialisation de mot de passe et de convocation Tour 3.

Correctif Dans chaque fonction d'envoi, récupérer le résultat et lever une erreur si error est non nul — allSettled comptera alors correctement, et l'écran de validation pourra afficher les échecs.
Élevé H-03 · reproduit

Le coefficient par défaut plafonne toutes les notes à 1 point

Le formulaire de création d'épreuve propose pour chaque critère un champ « Coeff. » initialisé à 1. Cette valeur est enregistrée dans weight — et POST /api/evaluations interprète weight non pas comme un coefficient, mais comme le nombre de points maximum du critère.

Épreuve créée avec les valeurs par défaut du formulaire (coefficient = 1) saisie 15 → 400 La note pour le critère "Motivation" ne peut pas dépasser 1 points. saisie 10 → 400 La note pour le critère "Motivation" ne peut pas dépasser 1 points. saisie 2 → 400 La note pour le critère "Motivation" ne peut pas dépasser 1 points. saisie 1 → 201 enregistré

Une épreuve créée sans passer manuellement chaque coefficient à 20 est donc notée sur 1 point par critère. Trois interprétations coexistent pour la même valeur : « coefficient » dans le formulaire admin, « points max » dans l'API et dans la grille de notation, et « rien du tout » dans le calcul de moyenne de la délibération.

Correctif Renommer le champ en « Points max » et porter la valeur par défaut à 20 — c'est déjà le repli utilisé partout dans le code (q.weight || q.maxScore || 20). Vérifier ensuite les épreuves déjà créées en production : celles laissées à 1 sont impossibles à noter normalement.
Élevé H-04 · reproduit

Une épreuve « sur table » n'est notable par aucun examinateur

Les épreuves de type commune fonctionnent par convocation globale : l'interface candidat masque volontairement l'inscription, donc ces épreuves n'ont ni créneau ni inscription. Mais canEvaluate() exige précisément d'être affecté à un créneau où le candidat est inscrit. Aucun examinateur ne peut donc saisir de note sur une épreuve sur table.

EXAM1 → note CAND1 sur l'épreuve commune → 403 NOT_ASSIGNED_TO_SLOT ADMIN → note CAND1 sur l'épreuve commune → 201 (l'admin contourne canEvaluate)

La règle de cloisonnement est saine — c'est exactement ce que tu voulais vérifier, et elle tient partout ailleurs. Le problème est qu'elle n'a pas de porte d'entrée pour le format « tout le monde en amphi ».

Correctif Deux options : autoriser explicitement la notation d'une épreuve commune à tout membre (le cloisonnement par créneau n'a pas de sens pour ce format), ou créer un créneau « amphi » avec inscription automatique de tous les candidats convoqués.
Élevé H-05 · reproduit

N'importe qui peut écrire un message sous un faux nom

Dans POST /api/messages, sender_id et sender_role sont bien dérivés du jeton — mais sender_name, qui est le champ affiché dans la messagerie, est recopié tel quel depuis le corps de la requête.

POST /api/messages (jeton candidat) body : { recipientId: <examinateur>, message: "…", senderName: "Admin AJC" } → 201 { senderName: "Admin AJC", senderRole: "candidate" }

Un candidat peut donc écrire à un examinateur en se présentant comme l'administration. Le rôle réel est stocké, mais rien ne garantit qu'il soit affiché à côté du nom.

Correctif Ignorer senderName du corps de requête et reconstruire le nom côté serveur depuis members ou candidates à partir de user.id.
Moyen M-01 · reproduit

La moyenne affichée en délibération mélange les barèmes

getAvgScore() additionne toutes les notes de tous les critères de toutes les épreuves, puis divise par le nombre de critères. Le barème de chaque critère est ignoré, et le nombre d'examinateurs aussi.

Tant que toutes les épreuves utilisent le même barème, le chiffre reste comparable. Dès que deux épreuves ont des barèmes différents — ce que le formulaire autorise — la moyenne perd son sens : un 1/1 et un 1/20 pèsent identiquement. Un candidat noté par deux examinateurs voit aussi cette épreuve compter double par rapport à un candidat noté par un seul.

Correctif Normaliser chaque note sur son barème (score / weight) avant de moyenner, et moyenner d'abord par épreuve avant de moyenner entre épreuves.
Moyen M-02 · reproduit

Les candidats n'ont aucun accès aux notifications

GET /api/notifications répond 403 à tout jeton candidat, alors qu'admin et examinateurs obtiennent 200. Toute notification destinée à un candidat — créneau annulé, changement de jury, convocation — est donc inatteignable depuis son espace.

À trancher Soit les candidats doivent recevoir des notifications dans l'app et il faut lever le 403 en filtrant sur leur identifiant, soit le canal candidat est l'email uniquement — auquel cas il n'y a rien à corriger, mais H-02 devient d'autant plus urgent.
Moyen M-03 · reproduit

Périmètre large pour les examinateurs non-admin

Un examinateur simple obtient 200 sur /api/candidates (fiches complètes de tous les candidats) et sur /api/kpis/global. L'export CSV, la liste des salariés et le suivi des évaluateurs sont eux correctement réservés à l'admin.

Ce n'est pas une faille au sens strict — un jury a besoin de voir les dossiers. C'est un choix à valider : aujourd'hui, tout membre du staff peut lire les coordonnées de tous les candidats, y compris ceux qu'il n'examine jamais.

Moyen M-04 · reproduit

Deux routes internes lisibles par un candidat

/api/settings (heures d'ouverture, durée de créneau) et /api/tour3/obligations (nombre de candidats et de membres par pôle) répondent 200 à un jeton candidat. Aucune donnée personnelle d'autrui n'y transite, mais tour3/obligations expose la tension de recrutement pôle par pôle — une information stratégique qui peut influencer le classement des vœux.

GET /api/tour3/obligations (jeton candidat) → 200 {"obligations":[{"pole":"Marketing","candidatsCount":2,"membresCount":4,…}, {"pole":"Audit Qualité","candidatsCount":2,"bureauCount":2,…}]}

Le scénario joué

Trois tours complets, avec pour chaque étape une tentative légitime et une tentative illégitime, afin de vérifier que la règle bloque bien ce qu'elle doit bloquer.

  1. Les trois types d'épreuve, business game inclus

    Une épreuve sur table, quatre entretiens individuels et un business game de deux groupes de deux candidats. Les trois examinateurs se sont inscrits sur les créneaux, avec un troisième volontairement laissé hors du premier business game pour servir de témoin. Quatre candidats répartis, notation individuelle et collective, fil de commentaires partagé entre examinateurs du même groupe, messagerie privée. Puis délibération : trois admis, un refusé.

  2. Vœux de pôles et entretiens de motivation

    Les trois admis classent trois pôles chacun, avec option bureau et poste précis pour la trésorerie. Trois créneaux d'entretien, jury de deux examinateurs. Le candidat refusé au tour 1 a été testé sur chaque action du tour 2 — vœux et inscription — et bloqué à chaque fois. Délibération : deux admis, un refusé.

  3. Entretiens finaux, vœux définitifs et verrouillage

    Les deux finalistes rejouent au tour 3 exactement les mêmes pôles et les mêmes rangs qu'au tour 2 — le cas qui cassait auparavant. Enregistré sans erreur, avec conservation de l'historique des vœux du tour 2. Confirmation définitive, verrouillage, tentative de modification après verrou refusée, correction par l'admin toujours possible. Délibération finale, puis réouverture d'un tour verrouillé pour corriger une décision.

Ce qu'il te reste à faire

Avant tout le reste

  1. Régénérer le JWT_SECRET en production et redéployer. C'est la seule action qui révoque la clé publiée. Je ne peux pas la faire à ta place : elle déconnecte tout le monde et touche la production.
  2. Vérifier que le correctif des vœux est bien appliqué en production. La colonne candidate_wishes.tour existe en prod, donc la migration a été posée — mais je n'ai pas pu vérifier en lecture seule si les anciennes contraintes uniques ont été supprimées. Si elles subsistent, le tour 3 cassera pour la plupart des candidats.

La requête à lancer dans l'éditeur SQL Supabase :

SELECT conname FROM pg_constraint WHERE conrelid = 'candidate_wishes'::regclass AND contype = 'u'; -- Attendu : aucune ligne. -- Si "candidate_wishes_candidate_id_pole_key" ou "…_rank_key" apparaît, -- appliquer la section 2 de MIGRATIONS_A_APPLIQUER.sql immédiatement.

Limites de cet audit

  • Aucune des trois fenêtres Chrome n'avait de session active — elles retombaient toutes sur /login. Je ne peux pas saisir d'identifiants moi-même, donc l'audit a été mené par appels API depuis un sandbox local exécutant le même code que la production, et non en cliquant dans l'interface avec tes comptes.
  • Ce qui n'est donc pas couvert : les bugs purement visuels, les états d'interface, la navigation, le rendu mobile. Tout ce qui est logique métier et contrôle d'accès l'est.
  • Je n'ai rien écrit dans la base de production. Les deux seules requêtes lancées vers la prod étaient des contrôles de schéma en lecture seule, sans donnée personnelle.
  • Les quatre candidats et les épreuves créés vivent dans le sandbox local uniquement.

Pour aller plus loin

  • Si tu ouvres toi-même les sessions dans Chrome, je peux reprendre l'audit côté interface — je piloterai des onglets déjà connectés sans jamais toucher à un champ mot de passe.
  • L'équité de charge du dispatch est bonne par épreuve, mais elle est recalculée à zéro à chaque épreuve. Sur l'ensemble d'un recrutement, un examinateur peut cumuler beaucoup plus de créneaux qu'un autre. Ce n'est pas un bug, c'est un choix documenté dans le code — à revoir si la charge devient un sujet entre membres.
  • Deux allocateurs coexistent toujours : runDispatch (via la sauvegarde des disponibilités) et runAutoAllocate (via toggle-member et /slots/auto-allocate). À unifier avant qu'ils ne divergent.
